# 工作区、备份与开发规范

适用于本地或 SSH 远端的项目整理与开发。只读检查和纯文档修改不强制备份。用户指定的位置优先于以下默认规则。

## 确定 xxm 根目录

1. 优先复用已有且可写的 xxm：先检查用户明确指定的位置、当前项目及其祖先目录、当前工作目录及其祖先目录；Windows 再检查已挂载本地各盘根目录的 xxm。只检查这些明确候选，不递归扫描整台电脑，不探测未授权网络盘。
2. 多个候选并存时，已有项目所属的 xxm 优先，其次当前工作区所属 xxm；其他候选选空间充足、可写且可用空间最多的位置。不要因其他盘空间更多而搬迁现有项目。
3. 没有可用 xxm 时：Windows 选择可写且剩余空间最大的本地非系统固定盘，创建该盘根目录的 xxm；Linux 在任务工作区根目录使用 ./xxm。Windows 没有适合的非系统盘时，也在任务工作区根目录使用 ./xxm，不擅自提权或更改磁盘设置。
4. 一次任务确定后固定其绝对路径，后续所有 ./xxm 都指向它，不能随 cwd 改变或创建 xxm/xxm。位置不可写或容量不足时先检查其他明确候选；确实无法完成时报告具体阻碍。

## 项目与私密状态

- 每个项目在 xxm 下有独立子目录，源码、项目依赖、构建产物和项目脚本归属清楚；不同项目不混放，不把文件散放在 xxm 根目录。
- 已有外部项目可原地工作，不为整理目录移动已安装应用、正在使用的项目、服务路径或快捷方式。
- xxm/.codex 用于目录级配置，不作为项目目录。
- 备份统一放 xxm/beifen/<项目名>/，在项目仓库之外，不能把备份套进下一次备份。
- 凭据、配对状态及运行日志遵循应用自己的私密目录约定，不提交 Git。Pro 默认 ~/.ssh-relay-pro 的身份和配对目录保持原位，不为整理而迁移或删除。

## 修改前备份

- 修改项目代码或配置前先识别项目根目录，按一组可独立回退的修改建立时间戳源码 ZIP，命名 <项目名>_vYYYYMMDD_HHmmss_before-change.zip；禁止覆盖。一次修改组可共用一次备份，无需每改一行备份一次。
- 包含自有应用源码、测试、构建脚本、配置模板、文档和必要静态资源；准确区分这些类别，不把测试或第三方代码冒称自有应用实现。
- 排除安装依赖、缓存、编译输出、发布运行包、日志、密钥、配对码、私密环境文件和运行状态。根据实际用途判断，不能只因目录名为 bin、build 或 env 就删除必要输入。可复现依赖用清单和 lockfile 记录。
- 确认归档可读取且覆盖本次修改涉及的原文件。备份无法完成时先尝试上述可用位置；仍失败则停止依赖该备份的代码修改，说明原因和最小所需动作。

## 修改后验证

- 执行与改动相关的最小必要检查；存在开发入口时保持可运行、可调试。CLI、库或纯配置项目使用相应检查，不强求启动网页开发服务器。
- 没有明确要求就不额外编译发布包或 EXE；如任务本身包含构建或发布则执行对应验证。
- 报告实际结果和未验证范围。SSH 远端遵守同样规则，先核验目标身份；不因本任务自动向远端全局安装 skill、修改全局配置或系统自启动。

## 每个版本的源码与可运行包交付（强制）

- 适用于本项目及按本规范开发的每个项目、每个交付版本。每个版本必须把完整源码和对应的单文件夹运行包上传到项目仓库，不能只保留在开发机器、远端电脑或临时云端目录。只有源码、只有构建脚本、只有下载链接，或机器上曾跑通但未上传同一份运行包，均不算完成交付。
- 源码必须覆盖该版本自有实现、必要资源、依赖清单与锁文件、构建脚本及运行说明，能够对应到明确的版本和提交；第三方开源项目须注明来源、固定版本及许可证，不能冒称自有源码。
- “百分百可以单文件夹运行”是交付验收门槛：运行包完整解压到一个独立文件夹后，必须能按说明直接运行，包含所需的应用文件、运行时、生产依赖和资源；不能暗中依赖原开发目录、全局 Node/npm、未列明的系统组件、其他机器上的文件或开发环境缓存。应用依法保存在用户私密目录中的授权及运行状态不随包上传，首次授权要求须明确说明。
- 验证必须针对最终上传的那一份运行包：上传到云端后，从仓库重新下载，核对 SHA256，在独立干净目录解压，按公开说明启动并实际执行核心功能。不得用源码测试、静态检查、另行部署的目录、旧版本成功记录或“打包成功”替代。若分卷或使用仓库 Release 附件，必须从实际交付地址下载全部文件并完成同样验证，不能因 Git 单文件大小限制省略必要内容。
- 记录版本、源码提交、下载位置、包名、SHA256、验证日期、云端系统及架构、启动入口、所需条件、实际功能检查和结果。包或运行源码变更后，须对最终包重新验证。验证失败或未完成时，必须明确标为未通过，禁止宣称稳定、百分百可运行或交付完成。
- 云端验证须使用该包支持的平台：Windows 包必须在 Windows 云端实际运行，Linux 包必须在对应 Linux 云端实际运行；跨平台静态检查或 Wine 不等于 Windows 原生验证。图形程序还须实际启动图形界面；桌面双击安装/启动承诺须单独验证对应入口。云端通过不代表任意用户系统均兼容，支持的系统版本、架构和必要系统库必须写清楚。
- 特别大且无意义的冗余内容（缓存、重复运行时、无关样例、无关数据及调试垃圾等）可以排除；运行必需内容不能只因体积大而静默省略。确需外置的开源项目、运行时、模型或其他可下载依赖，必须随版本提供完整运行所需清单，逐项列出用途、固定版本、官方来源和可直接下载地址、校验值、许可证、放置路径、安装或准备步骤，以及是否需要网络、账户或权限。
- 有外置依赖的包必须显著标明“需按清单准备外部依赖”，不能冒称完全自包含或开箱即用；必须在干净云端严格按同一份清单准备依赖并验证成功。准备完成后的应用须可从约定的单一项目文件夹启动，不能依赖未公开的人工修补。
- 每个版本保留可追溯的源码、运行包、依赖清单、校验文件及脱敏验收记录，并提供用户可点击的对应下载链接。密钥、配对码、个人凭据、原始日志与私密状态仍禁止上传；在运行包内封装必要生产依赖不受“散装 node_modules 不提交 Git”的限制，须保留其许可证。
- 本条新增只建立后续强制交付要求，不自动使现有历史包通过验收；现有版本是否合格必须按同样流程逐个核验。纯文档/skill 修改无需为此额外构建应用运行包，也不能宣称新增应用运行验收。
