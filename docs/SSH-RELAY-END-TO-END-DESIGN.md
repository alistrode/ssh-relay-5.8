# SSH Relay：面向 CLI、MCP 与 Agent Harness 的端到端连接设计原型

- 日期：2026-10-19（北京时间）
- 状态：设计提案，待实现和验收；不代表现有版本已经支持本文全部能力。
- 目标代码基线：`fix/ssh-pro-startup-20261019`，设计开始时分支提交为 `99324dddf32663e96cc6b0235eb63f4ae992e6d0`。
- 范围：连接、授权、执行、文件、恢复、诊断以及 AI 接入。本文不修改代码、不删除现有 skill、不交付新版运行包。

## 1. 产品定位与目标

SSH Relay 是面向 CLI 和 MCP 的远程操作软件。用户在两端运行软件，以一串连接码完成首次配对，之后使用设备 ID 连接。软件承担配对、端到端加密、身份验证、凭据管理、断线恢复与操作结果跟踪。

AI 依靠 CLI 帮助或 MCP 工具 schema 即可使用，不需要阅读连接 skill，也不需要管理 near/far、状态目录、连接报告、指纹配置和恢复循环。桌面界面只作为未来可选外壳，不是本方案的交付前提。

核心用户流程：

```text
被连接电脑启动 relay → 生成一次性连接码 → 分享连接码
发起端 connect → 获得已验证设备 ID → exec / files / sessions
普通断线 → 软件自动恢复原设备连接 → 查询原操作结果
```

不要求用户自建中继，不要求为普通使用安装系统 Node、Python 或 OpenSSH。运行包应内置必要运行时与依赖；源码开发依赖另行列出。

## 2. CLI、MCP、Harness 与云端的关系

| 概念 | 本方案中的含义 |
|---|---|
| 模型 / AI 助手 | 根据用户意图选择工具和解释结果 |
| Agent harness | 编排模型、工具、权限、上下文和生命周期的运行系统 |
| CLI | 可由用户或 harness 的终端工具调用的程序入口 |
| MCP server | 按 MCP 协议提供工具的适配层，由支持 MCP 的客户端 / harness 接入 |
| 云端 Linux 环境 | 执行程序的机器或容器，可运行 CLI、后台服务和 MCP server |
| 桌面客户端 | 可选界面；与 CLI/MCP 复用同一核心服务 |

云端是运行位置，CLI 是程序接口，harness 是编排系统，三者不互斥。AI 在云端通过终端运行 relay CLI，并不意味着 AI 本身就是 CLI。

当前讨论中的助手通过 Codex harness 提供的工具访问 /workspace 云端工作区，能够执行 shell。不能据此断言用户前端就是 Codex CLI，也不能推定该 harness 支持运行时动态注册任意 MCP server。

因此必须同时提供两条完整路径：

1. **CLI 路径**：harness 有 shell 即可调用 relay；无需动态加载 MCP。
2. **MCP 路径**：客户端配置 relay MCP server，发现工具后直接调用。

软件不能只启动 MCP server 就宣称当前 AI 已接入。MCP 接入成功须有客户端侧工具发现与实际调用证据。

## 3. 架构

```text
发起端机器                                    被连接端机器
用户 / AI harness
       │
       ├── shell → relay CLI ─┐
       └── MCP → relay MCP ───┤
                              ▼
                    本机连接核心服务
                    设备 / 授权 / 操作
                              │
                              └── 公共中继转发密文 ── 对端连接核心服务
                                                        │
                                              受授权的执行与文件服务
```

CLI 和 MCP 共享业务核心与当前账户的私密状态。MCP stdio 可以是按需启动的适配进程；核心服务负责持续连接。stdout 仅输出协议或机器结果，诊断写 stderr，避免破坏 MCP。

内部模块：

| 模块 | 职责 |
|---|---|
| 本地服务管理 | 单实例、按需启动、就绪检查、版本协商 |
| 配对服务 | 连接码、握手、单次消费、超时与撤销 |
| 身份与授权库 | 本机密钥、对端身份、客户端能力与授权期限 |
| 连接管理 | 心跳、业务探测、恢复、并发通道与中继切换 |
| 操作管理 | 操作 ID、去重、状态、结果记录、取消 |
| 文件服务 | 分块传输、校验、冲突策略与恢复 |
| CLI/MCP 适配 | 相同语义与错误模型的两种接口 |
| 诊断 | 脱敏事件与按阶段故障定位 |

本地服务只使用当前账户可访问的 IPC。Linux 优先 Unix domain socket，Windows 优先具备账户 ACL 的 named pipe。若使用回环 HTTP，必须有本地身份认证、请求来源检查及凭据保护；仅监听 localhost 不等于访问安全。

## 4. 端到端协议与连接码

端到端加密不等于网络路径必须 P2P。第一版继续使用现有公共中继，但设备身份认证、业务密钥和业务解密均在两端完成。中继不能执行远端命令或读取命令、文件、结果；仍可能观察连接时间、流量大小和可见路由标识，不能声称元数据完全隐藏。

连接码格式示意：

```text
SRP1-XXXX-XXXX-XXXX-XXXX
```

最终长度和编码由密码学评审决定，要求足够随机、避免混淆字符并能检测输入错误，不承诺六位数字足够安全。二维码或 URI 是同一凭证的不同表示，不能增加权限。

默认五分钟有效、单次配对、可取消，重新生成使旧码失效。码仅引导首次授权，不是永久密码，不包含设备私钥或长期业务凭据。

现有 OPAQUE 配对和 SSH 身份机制是候选基础。实现前检查握手身份绑定、密钥派生、消息认证、重放保护、降级保护、版本协商及随机数来源；不自行发明密码算法。

配对流程：

1. 两端分别在本机生成身份密钥。
2. 被连接端生成有期限的配对邀请，将本次授权策略绑定到邀请。
3. 发起端通过连接码完成认证的配对握手。
4. 双方交换并绑定设备公钥与授权信息。
5. 被连接端原子消费邀请并持久化客户端授权。
6. 发起端持久化对端身份，完成可重试的配对确认。
7. 建立业务通道，核验真实账户、系统与可用能力。
8. 返回 ready；如果配对已完成但通道失败，返回已配对且连接中，不能要求立即生成新码。

配对确认丢失时，同一次握手可安全取回结果；不同客户端不能重复消费。限制失败尝试、并发与消息大小，避免资源耗尽。恶意中继可能阻断服务，不能承诺中继失效时仍可连接。

## 5. CLI 功能原型

以下命令均为拟议接口，尚未实现。无参数命令必须返回简短帮助，不自动开放远程访问。

```sh
relay --help
relay version --json
relay serve
relay invite create --permission development --remember --json
relay invite cancel --invite-id inv_example --json
relay connect --code-stdin --json
relay connect --device dev_example --json
relay devices --json
relay exec --device dev_example --request-id req_example --command-stdin --json
relay operation status --id op_example --json
relay operation cancel --id op_example --json
relay disconnect --device dev_example --json
relay forget --device dev_example --json
relay doctor --json
```

### 5.1 被连接端

`relay serve` 在前台运行，适合终端或容器。可选的后台安装、自启动或系统服务必须是显式独立动作。邀请命令可复用已运行服务；本地客户端辅助服务可以按需启动，但不应因此自动开启被连接能力。

`invite create` 返回邀请 ID、到期时间、权限和连接码。只有此项显式输出可以包含连接码，普通 status、日志与诊断不得返回它。交互模式清晰展示“持有码即可获得本次授权”。

支持两种邀请策略：持有码即可配对；本机确认后配对。无人值守流程使用前者，不为每次普通重连新增确认。

### 5.2 发起端

连接码由 stdin 或受限权限文件传入，避免出现在进程参数和 shell 历史。交互终端可使用隐藏输入。不得把用户连接码拼进 shell 命令，也不得通过 echo 实参传递。

成功输出包含 device_id、实际 hostname/account/platform、授权能力、验证时间和连接方式。所有后续业务操作显式携带 device_id；设备别名只用于显示和选择，不能代替密钥身份。

### 5.3 机器输出约定

单次命令的 --json 输出一个完整 JSON 对象；事件流使用单独 --jsonl 模式。长操作可返回 operation_id，由查询命令获取进度和结果。stdout 无装饰性日志。

建议退出码：0 成功；2 参数错误；3 配对失败；4 当前不可达；5 授权拒绝；6 身份异常；7 操作失败；8 结果未知；9 不兼容。精确原因由稳定 error.code 表达，避免仅靠数字区分所有错误。

## 6. MCP 接口原型

工具名和参数是设计契约，最终应以发布的 schema 为准：

| 工具 | 核心参数 | 职责 |
|---|---|---|
| connect | code 或 device_id，二选一 | 配对或连接既有设备 |
| devices | 可选状态过滤 | 列举设备与当前验证状态 |
| disconnect | device_id | 断开并暂停自动恢复 |
| forget | device_id | 撤销并删除配对 |
| exec | device_id、command、request_id | 提交命令 |
| operation_status | operation_id | 查询进度、结果与不确定状态 |
| operation_cancel | operation_id | 请求取消 |
| files_upload / files_download | device_id、明确两端路径、冲突策略 | 文件传输 |
| session_open / session_exec / session_close | device_id 或 session_id | 有状态执行会话 |

成功示例：

```json
{
  "status": "ready",
  "device_id": "dev_7f2a",
  "name": "办公电脑",
  "hostname": "DESKTOP-ABC",
  "platform": "windows",
  "account": "DESKTOP-ABC\\zhangsan",
  "permission": "development",
  "identity_verified": true,
  "capabilities": ["exec", "files", "sessions"]
}
```

客户端配置一次稳定 MCP 入口。新设备通过 connect 添加，不修改 MCP 配置，不为每台设备启动一份 MCP server。

工具 schema 直接说明目标、路径、权限和错误语义。不以隐藏长指令、必读 prompts 或资源文件替代原连接 skill。既有业务工具按能力保留并逐步兼容，但不强制每个客户端一次加载所有工具。

连接码经过 AI 对话或 MCP 调用时，外部客户端可能保留聊天与工具记录。软件只能保证自身日志脱敏，不能承诺客户端完全不留痕。用户也可在近端 CLI 或本地界面完成配对，然后只向 AI 提供设备 ID。

## 7. 安装与首次接入

CLI 路径：下载对应系统运行包，校验并解压，执行包内 relay；harness 的 shell 直接调用该绝对路径，不依赖全局 PATH。

MCP 路径：生成所选客户端的配置预览，用户请求安装时写入对应配置，然后验证客户端发现工具并执行只读检查。不支持动态注册的 harness 应通过既有配置流程加载，或者立即改用 CLI 完成同样工作。

云端容器必须有持久化私密目录才能跨环境重建保留身份；临时文件系统销毁后不能承诺自动恢复授权。备份身份材料需显式安全导出，不把凭据存入仓库。

本机服务与 MCP 必须正确处理进程退出、客户端重启和版本不兼容，不把端口存在或进程存活当作连接成功。

## 8. 身份、权限与多客户端

设备身份、授权、会话和操作分开记录。权限由接收端检查，发起端隐藏按钮不能代替权限控制。

| 模式 | 能力边界 |
|---|---|
| 只读 | 受控信息查询、目录列表、文件下载；不开放任意 shell |
| 开发操作 | 运行命令、读写文件和会话，受实际系统账户权限约束 |
| 自定义 | 工具级能力、文件服务目录范围、授权期限 |

任意 shell 能够访问远端账户可访问的资源，不能同时宣称严格只读或目录隔离。需要更强隔离时使用专用账户或真正的沙箱。普通连接不自动提权、不修改 UAC 或系统 ACL。

每个客户端使用独立密钥、授权 ID 与通道。允许同时连接，单个客户端断开或撤销不抢占其他客户端。

disconnect 保留授权，但暂停本端主动重连。远端 revoke 撤销指定客户端并关闭其会话；forget 尝试远端撤销后删除本地状态。远端不可达时，明确返回 remote_revocation_pending，不得把本地删除冒称远端已经撤销；如用户继续本地删除，应说明需要在接收端撤销残留授权。接收端撤销是最终权威。

临时授权必须有最大有效期；接收端观察到会话结束或租约超时后失效，避免单靠瞬时断网事件判断授权结束。长期授权有效至撤销或用户设置的期限。

## 9. 状态机与恢复

分别建模：

- 授权：unpaired、pairing、authorized、expired、revoked。
- 连接：offline、connecting、ready、reconnecting、disconnected、identity_error。
- 操作：queued、running、succeeded、failed、cancel_requested、cancelled、unknown。

ready 要求通过对端密钥认证并验证实际业务通道。心跳在线只代表近期可达，不能证明新命令已经执行。

沿用先快速尝试、再有界指数退避的恢复策略，加入抖动和单实例协调。恢复循环属于服务，AI 不需要执行循环、重启服务或索要新码。授权撤销、身份异常、用户断开时停止对应自动恢复。

长时间连接调用返回 connecting/reconnecting 和可查询 ID；不无限占用一次工具调用。恢复后重新验证对端，不默默切换设备，也不自动重放业务写入。

## 10. 命令、会话与结果

发起端生成 request_id；接收端在启动操作前记录去重关系和 operation_id。相同请求 ID、相同内容返回既有操作；相同 ID、不同内容拒绝。去重范围绑定授权客户端及设备，保留期限明确。

操作记录含开始/结束时间、退出码、输出范围与状态。大输出限额并提供按偏移读取，结果保留时间可配置；过期返回 result_expired，不伪造成功。

不承诺任意 shell 的“恰好一次执行”。进程崩溃或外部副作用可能造成无法确认，必须返回 unknown，禁止自动重新执行部署、删除或数据库导入。

取消分为已请求、进程已停止、无法确认；取消不代表回滚。持久会话与连接会话分离；仅实际保留的远端进程才能续用。PTY 能力按实际实现声明，不能因提供 session 工具就承诺交互终端。

Windows 默认 PowerShell、Linux 默认 POSIX shell，返回实际执行器信息；参数与脚本内容不能未经转义拼接。

## 11. 文件传输

上传和下载均绑定 transfer_id、源端与目标端路径、文件大小、内容校验和及冲突策略。

流程：创建任务 → 分块传输与接收确认 → 完整校验 → 最终写入 → 返回完成证据。目标先写临时文件，同一文件系统且平台支持时以原子替换完成提交；不支持时明确降级语义。

恢复前检查源文件未变化、临时块仍有效与授权仍有效。冲突策略必须显式选择拒绝、覆盖或另存。临时文件有生命周期与清理机制，不无限积累。

路径限制检查目录穿越、符号链接和 Windows 重解析点；仅字符串前缀判断不构成目录隔离。近端 local_path 与远端 remote_path 明确区分。

## 12. 错误与诊断

统一错误包含 code、stage、message、retryable、device_id、operation_id（如适用），不包含秘密。

| 错误码 | 行为 |
|---|---|
| INVALID_ARGUMENT | 本地拒绝，返回参数说明 |
| PAIRING_FAILED | 不能确定时统一说明码无效、过期或不可用 |
| PEER_OFFLINE | 有限等待后返回，按授权策略恢复 |
| RELAY_UNAVAILABLE | 区分本机网络与中继不可达 |
| IDENTITY_MISMATCH | 阻断业务连接，不自动信任新身份 |
| AUTHORIZATION_REVOKED | 停止恢复 |
| PERMISSION_DENIED | 区分工具授权与系统权限 |
| OPERATION_UNKNOWN | 查询状态，不重放 |
| VERSION_INCOMPATIBLE | 返回两端版本和必要升级范围 |

doctor 提供本地服务、网络、中继、配对、身份、业务通道各阶段结果。不以 broker PUBACK、端口监听或旧报告证明端到端成功。诊断默认脱敏，排除密钥、连接码、命令正文、文件内容及原始敏感路径。

## 13. 数据与兼容迁移

持久化实体：本机身份、设备、客户端授权、邀请、操作记录、传输任务；连接状态与在线时间不能冒充永久身份。状态文件具备 schema 版本与事务/原子写入，权限仅限当前账户。

兼容现有授权必须校验来源、权限和身份材料，不静默导入旧连接块，不因普通迁移生成新设备身份。先完成新接口及兼容验证，再移除连接 skill、AGENTS/README 强制引用以及长 MCP 连接说明。保留简短 CLI 帮助与维护文档。

第一版不要求把 MQTT 换成新传输协议，不增加远程桌面、屏幕控制或通用 NAT 穿透作为必备范围。现有 SSH/MCP 业务能力在授权允许且依赖具备时继续保留；数据库等外部依赖如实声明。

| 阶段 | 可评审结果 |
|---|---|
| A 核心服务 | 稳定设备 ID、状态机、本地 IPC、单实例与自动验证 |
| B CLI 闭环 | invite/connect/devices/exec/operation/files/doctor，机器输出与退出码 |

阶段可迭代，不能先删 skill 再把缺失功能交给 AI 猜测。文档提交不等于任何阶段已经实现。

## 15. 验收矩阵

| 场景 | 通过条件 |
|---|---|
| 无 skill 的 CLI-only harness | 仅靠 --help 和 JSON，完成配对、命令与文件往返 |
