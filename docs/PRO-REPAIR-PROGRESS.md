# SSH Relay Pro 2.0.1 修复进度

更新日期：2026-10-19
状态：候选修复中，Windows 闪退尚未修复，当前候选包未通过验收。

## 结论

目前不能把 Windows 包称为可用或交付完成。已在一台 Windows 11 x64 机器上复现启动失败，并抓到比弹窗更早的 Chromium 启动日志：GPU 子进程以错误码 18 启动失败，随后渲染进程无法启动，Electron 主进程以 `0x80000003` 退出。改用常规桌面启动、从桌面快捷方式启动，以及官方 Electron 43.8.0 对照运行，仍然失败。43.8.0 对照没有进入项目包，不能作为候选版本的修复。

用户报告 Defender 曾拦截该包，放行后仍然闪退。检查当时可查询的 Defender 威胁/检测记录，没有找到与这些测试文件名相符的记录；这不足以证明 Defender 与故障无关。运行文件的 Authenticode 状态为未签名，也不能单凭这一点判定文件有害。

## 已取得的证据

- 测试机器实际报告为 Windows 11 `10.0.26200` x64。虽然连接标记写着 `win10`，这次验证不能算 Windows 10 验收。
- 原 Pro 2.0 桌面程序和候选提取目录中的应用文件已逐项比较：共同文件中有 4567 个字节一致；唯一变化的共同文件是 `BUILD-PRO.json` 元数据。应用主要源码和 Electron 主程序文件一致。这说明当时的闪退不能仅用“新 ZIP 解坏了”解释。
- 原 Electron 44.8.0 与从 Electron 官方发布校验值确认来源的 43.8.0 对照包，都出现 GPU 错误码 18 和同类主进程退出。对照测试仅用于缩小问题范围，没有改变仓库固定的运行时版本。
- 曾出现 `EPIPE` 主进程异常。检查栈后发现它来自向已关闭的标准输出/错误管道写入。代码已增加只忽略 `EPIPE`/`ERR_STREAM_DESTROYED` 的处理；其他写入错误仍会抛出。回归检查覆盖标准输出断开、标准错误断开和无关错误三种情况，结果通过。它修复的是日志管道异常，不是目前观察到的 GPU 启动失败。
- Linux 上此前对旧 Pro 2.0.0 包做过 Debian 12 XFCE/Xvfb 的文件管理器双击和桌面图标重开验证。那不是当前 2.0.1 候选包，因此不能算当前包的验收。

## 日志修复进度

已在源码中接入统一的 GUI 诊断记录，并将它放在 Electron 和后台启动模块载入之前初始化，目的是在窗口未出现或渲染器未启动时也留下启动记录。当前实现记录启动阶段、窗口加载/显示、GPU/渲染进程退出、未捕获异常和退出等事件，并以运行 ID 关联启动器、Electron Chromium 原生日志和 GUI 日志。

诊断导出设计为离线读取本机文件，不需要 near/far 后台先成功启动。Windows 启动器会记录每个解包和校验阶段、GUI PID、退出码及 Chromium 日志位置；同一目录提供诊断导出入口。日志有大小和保留份数上限，并对凭据字段、配对码、私钥、URL、命令和本地路径做过滤。日志目录预期位于用户配置目录下的 `logs`；Windows 启动时的阶段记录也会留在包旁的 `SSHRelayPro/logs`。

以上属于源码实现状态。**新的诊断模块、脱敏覆盖、轮转行为、Windows PowerShell 启动器语法和最终 ZIP 内导出流程尚未完成本轮验证**，所以不能保证每类闪退都会完整留痕，也不能称日志子系统验收通过。Electron 在 JavaScript 初始化前即崩溃时，最早能看到的记录仍可能只有启动器和 Chromium 原生日志。

## 2026-10-19 修复续接（候选，非最终交付）

在 `fix/ssh-pro-startup-20261019` 独立工作区继续修复，修改前源码备份留在仓库外。已确认首次连接的实际 Windows 11 进程为低完整性（RID 4096），用户目录和已有工作区新建文件夹均被系统拒绝；用户从管理员终端重启原远端后，身份核验仍为同一目标，令牌变为高完整性（RID 12288）。这一证据确认了当前调试通道的权限问题，不足以单独证明历史 GPU 错误 18 的唯一原因。

新增 GUI 初始化前的结构化日志、限定字段的离线诊断导出、GPU/渲染进程退出记录及输出管道保护；异常监视器不会吞掉致命异常。GUI 日志每份 256 KiB，保留三份轮转副本；导出对每份文件限量读取，跳过损坏行，并仅提取 Chromium 原生日志的固定故障码计数，不导出路径、原始消息或凭据。原生 Chromium 文件仅留在本机，保留当前与上一轮，尚不承诺运行过程中的大小上限。

按用户本轮明确要求，Windows `Start.cmd` 默认通过系统 UAC 请求管理员启动；已提权则直接启动，取消或失败时明确退出，不关闭 UAC、不修改 ACL、不注册自启动。`Diagnostics.cmd` 只离线导出，无需提权。启动器保留调用者的配置目录，并记录 UAC 请求及启动阶段。直接运行 EXE 仍进行完整性预检，避免低完整性运行时仅显示 GPU 闪退。

本地 Node 检查：11 项通过，覆盖隐私过滤、损坏行、文件权限、轮转、符号链接、输出管道错误及既有 Pro 单元检查；Python 打包器编译、JavaScript 语法与 diff 检查通过。Windows 启动器、原生界面与最终下载包仍待实机验证；旧运行包不是本次 2.0.1 候选实现，不能算当前候选交付。

## 2026-10-19 独立云端修复检查点（尚未交付）

新增签名占用探测：近端取得新鲜远端占用状态后才尝试 SSH；其他控制器占用时先拒绝，远端提出保留/切换的原生弹窗。关闭、超时、拒绝或候选连接失败均保留当前控制器；批准后只在候选 SSH 就绪时提交所有权变更。旧连接已打开的命令、SFTP 句柄和 TCP 转发继续完成，新业务操作停止接收。探测者的中继 epoch 不再重置占用中的远端数据流。撤销其他设备授权只清理该设备，不重启远端全部连接。

云端 Linux 已通过 19 项单元检查、9 项真实 SSH/SFTP 切换检查及一次独立进程恢复；当前源码一小时连续检查进行中。Linux 原生 Electron 在 Debian 12 容器/Xvfb 中以非 root 和启用沙箱方式启动并捕获界面；这不等于真实桌面托盘或最终下载包验收。Windows 10 LTSC 云端已启动到桌面并有独立执行器；逐文件 SMB 部署超时，已转为单个归档在客体本地解压。此前未部署完整导致的缺文件检查不算应用验证通过。

共用虚拟机的短信息接入使用可重复 OPAQUE 邀请，为每次接入分配独立中继会话；实测同一邀请三端并发 SSH 控制台 HTTP 200，原维护端同时仍可用。此测试入口和用户电脑原有连接完全隔离，凭据不随源码或运行包交付。

### 跨平台时钟与转发保护

真实云端 Windows 与 Linux 的时钟相差约七小时，暴露出直接比较两端探测时间戳的兼容性问题。已改用远端生成的随机挑战：当前挑战每分钟轮换，两分钟后失效，签名绑定控制器、请求 ID 和挑战；不调整任一系统时钟。检查覆盖正负七小时偏差、错误挑战和过期重放。新的真实 SSH 集成共 10 项通过，包括切换后已有 TCP 转发继续通信、新建转发拒绝。运行源码因此变化，一小时检查已重新开始；前两段被中断的检查明确标为中断，不合并计时。
