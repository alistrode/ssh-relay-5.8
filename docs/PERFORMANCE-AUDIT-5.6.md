# 5.6 性能审查

日期：2026-10-27。审查基线：`ed18d72`；三处嵌入 PowerShell 的日志补丁回归已在 `372ad46` 修正。

结论：此前的界面响应优化真实存在且多数保留，但没有覆盖后来增加的进程身份检查、会话执行调度、客户端生命周期与文件恢复路径。当前的主要问题是同步等待、重复工作和轮询成本，不是已证实的内存泄漏。将启动等待从 20 秒延长至 90 秒是容错修正，不是启动加速。

## 证据及限制

- 核对了 `docs/5.1-UI-RESPONSIVENESS-DESIGN.md` 和操作记录；审阅 desktop、src/pro、MCP 发现/传输与 relay 路径。另对 66 个 desktop/pro JavaScript 文件做了 AST 字符串检查，确认修正后三处 PowerShell 字符串不再包含误植的 JavaScript 日志调用。
- Windows 独立探针：SYSTEM 身份、系统 Node 26.4.0；实际应用为 Electron 44.8.0 / Node 24.22.0、桌面账户。探针结果用于量化同一实现的成本，不冒充应用账户下的完整启动基准。
- Windows 首次进程身份查询 8,488 ms，其中启动时间查询 5,576 ms、进程查询 2,911 ms。预热后的两次 processState 分别 981、950 ms，每次仍执行两次 PowerShell，单次约 469–504 ms。
- 实际应用此前日志记录过约 24 秒的事件循环停顿。它与独立探针属于不同证据，不能直接相加。
- Windows 同步日志探针：2,000 条带 Error 的记录耗时 2,695 ms，约 1.35 ms/条，保留 3 个轮转文件。包括构建 Error、序列化、检查及写入成本。
- Linux 合成历史会话探针直接调用实际 SessionExecutions/ExecutionScheduler：64 个已关闭会话时，每个 Agent 调度周期两次快照合计 256 次同步读取、384 次 lstat、2 次 readdir，即 642 次同步文件系统调用；平均 2.92 ms。不能把该毫秒数当成 Windows 测量值。按现有 500 ms 周期约为 1,284 次调用/秒，另有授权核对开销。
- Windows 短时空闲采样：10 个进程，工作集求和约 145.7 MiB（共享页重复计算，并非独占内存）；约 3.16 秒内累计 CPU 增量 0.03125 秒。该短样本不支持持续高 CPU 或内存泄漏结论，也不排除长时间/负载下问题。
- 未重启现有客户端、未修改配对或身份、未对现有任务数据做压力注入。静态风险不等于全部已在用户负载中复现。

## 发现

### 1. P1：在启动及运行路径同步启动 PowerShell

位置：`src/pro/task-process.cjs:6-59`、`store.cjs:61-137`、`os-version.cjs:11-34`，以及任务/会话管理器初始化与会话存活检查。

processState 先验证当前进程，再查询目标，进程退出时还额外查询缺席状态。自身身份重复检查、启动时间缓存只在单个进程内存在；多个 Agent、runner 又各自重新启动 PowerShell。会话状态分页查询也会走 runnerLive / sameProcess；它不是只发生一次的启动成本。

建议：自身身份按本次进程生命周期缓存；系统启动身份由可信的启动上下文复用；目标检查改为异步、批量查询，或使用合适的 Windows 原生接口。保留 PID + 创建时间 + 系统启动身份校验，尤其终止进程前必须重新核验，不能用无限缓存换取误杀风险。

### 2. P1：一端慢会阻止下一轮两端刷新

位置：`desktop/renderer.js:65-84`、`desktop/main.cjs:40-46`。

虽然 near/far 各自能先更新一次，但下一轮调度要等 Promise.all 两端都完成。慢端若进入恢复等待，快端之后也停止更新。远端角色还在状态查询后串行请求 /pair/current。用户看到的是界面状态停住，不一定是渲染线程 CPU 卡死。

建议：两角色分别调度、各自合并在途请求；展示请求使用短超时及旧快照标记，恢复任务独立运行；将配对邀请与同一状态快照一起返回。不要自动重发写入命令。

### 3. P1：健康检查重试引发同步错误日志放大

位置：`src/pro/agent-client.cjs:109-146`、`runtime-log.cjs:24-29`。

失败健康检查约每 200 ms 重试；同一次错误既记录 caught_error，又记录 agent_health_failed。两个角色持续失败时形成高频、重复的完整堆栈与同步文件操作。轮转限制了磁盘占用，却没有消除序列化及阻塞写盘成本。这是本轮日志补丁仍需改进的地方。

建议：同一个失败事件只记录一次；相同健康失败保留首次堆栈、首次/末次时间及准确计数，周期性输出汇总；普通日志有界批量写入，致命错误同步落盘。不能为了性能直接丢弃不同错误。

### 4. P2：共享调度器每轮被重复调用，已关闭会话继续被扫描

位置：`agent.cjs:492-498`、`tasks.cjs:194-215`、`session-manager.cjs:158-161`、`session-executions.cjs:16-53`。

Agent 先调用 TaskManager.tick 再调用 SessionManager.tick，两者都调用同一 scheduler.tick；session snapshot 每次扫描全部会话目录、配置和 manifest，之后才排除已关闭会话。64 个已关闭会话的 642 次同步文件系统调用/周期已在合成探针量化。任务快照还会遍历最多 10,000 条历史记录筛选待执行任务。

建议：每个 Agent 周期只推进一次共享调度器；维护活动/排队索引，将终态记录从热路径排除；启动时恢复历史、运行时增量更新。不要破坏持久化执行声明及未知任务占位规则。

### 5. P2：空闲持久会话仍以 20 Hz 轮询磁盘

位置：`session-runner.cjs:90-137`。

每个 runner 每 50 ms 检查撤销、关闭及 inbox，另有一个每 50 ms 的完成检查。64 个空闲会话意味着仅前者就有约 1,280 次轮询/秒；另有两秒一次的持久心跳。

建议：活动期保持需要的响应速度，空闲时退避；使用受控 IPC/通知加低频兜底扫描；合并纯内存完成检查。撤销和取消必须有明确的最大响应延迟。

### 6. P2：每个文件 RPC 都新建 Worker，且每块串行确认

位置：`file-service.cjs:23-46`、`file-worker.cjs`、`src/mcp/file-transfers.js`。

把大文件工作移出 Agent 是正确方向，但当前每次 status/block/commit 都 new Worker，加载模块、授权文件、日志入口后又退出，不是复用的两线程池。上传每个 1 MiB 块还要等待 SFTP 写入和一次 control 确认，然后继续下一块。Worker 初始化和中继往返会逐块累计；本次未单独测量其 Windows 吞吐占比。

建议：使用有界常驻 worker 池或每次传输复用工作线程；采用有界流水线。授权核验、内容散列、顺序提交和断线恢复确认必须保留。

### 7. P2：MCP 每次工具调用重新发现全部在线设备

位置：`src/mcp/config.js:18-27`、`agent-provider.js:57-96`。

每次 withServerSnapshot 读取整个设备列表，并为所有在线设备分别取连接描述；目标连接准备又会取一次描述。即便操作一台设备，也付出全局发现的成本。20 台在线设备会形成 N+1 个本地 API 请求，虽然描述请求是并行的。

建议：读取目标优先，或新增原子批量快照；使用带 generation/bootId 的受控缓存和失效事件。禁用、取消配对及身份变化不能被缓存掩盖。

### 8. P2：GUI 崩溃恢复先全量扫描和停止后台，再重开窗口

位置：`client-supervisor.cjs:51-65`、`client-lifecycle.cjs:72-112`。

GUI 异常退出与主动托盘退出共用了大量清理动作。Windows 清理反复枚举全机进程，按进程串行启动 taskkill，最多八轮；即使 /T 已经结束子树，后续列表仍有重复目标。会放大窗口恢复延迟并中断本来仍可用的连接。

建议：区分主动退出与异常重建；维护已知子进程树并批量核验。若设计允许，给 GUI 崩溃重建一个有界宽限期；不能擅自取消客户端与服务共同运行的既定约束。

### 9. P2：关闭的角色仍启动 Guardian + Agent，并持续维护文件状态

位置：`desktop/main.cjs:130-144`、`agent.cjs:492-518`、`client-lifecycle.cjs:11-19`、`client-supervisor.cjs:36-39`。

当前 near 已关闭，仍有对应 Guardian 和 Agent。每个 Agent 500 ms 检查客户端状态；Guardian 每秒检查；GUI 每两秒心跳并原子更新 JSON。它们反复读取归属、版本标记、运行信息。空闲采样没有显示当前 CPU 很高，但这是多进程启动和后台唤醒的固定成本。

建议：未启用角色延迟初始化，展示配置用轻量快照；只缓存可验证为本次进程生命周期不变的数据；用写入失效/IPC 心跳减少重复文件读取。

### 10. P2：打开日志面板时，全文件解析排序后只显示少量记录

位置：`agent.cjs:992-1014`、`desktop/renderer.js:86-88`。

每五秒读取四个 JSONL 文件、全部解析并排序，取最后 300 条发给界面；界面合并排序后仅展示 35 条。单文件已限大小，所以不是无限内存问题，但工作量与实际显示量不匹配，而且发生在 Agent 事件循环。

建议：有界尾部读取或内存 ring buffer，按游标增量获取。保留完整轮转文件供导出，不需要每次展示重新全量解析。

### 11. P2：本地大文件快照及校验仍会阻塞 MCP 进程

位置：`file-transfer.cjs:36-77`、`download-store.cjs:66-101`、`src/mcp/file-transfers.js`。

远端用了 Worker，本地上传快照复制、散列以及下载提交的全文件校验仍同步执行，影响同一 MCP 进程中其他工具的响应；不是直接阻塞独立的 Electron GUI。每块持久确认也增加串行成本。

建议：把本地大文件复制/散列迁至受控 worker 或异步流；保留源身份复核、散列和提交持久性。不能简单删除 fsync 或完整性校验。

### 12. P3：字体加载策略和软件渲染是可优化项，不是已证实根因

位置：`desktop/style.css:1-8`、`desktop/main.cjs:9`。

自带 CJK 字体采用 font-display:block，冷加载时文本会等待；软件渲染有兼容收益，也牺牲合成效率。没有该字体加载耗时或显卡 A/B 数据，不能将其断言为此前白屏的唯一原因。

建议：考虑 swap/系统字体先显示；拿到真实的图形崩溃与绘制指标后再决定恢复硬件加速，不移除 Chromium 沙箱。

## 已保留的有效优化

- 状态请求合并、刷新后等待而非无界重叠；隐藏时停止大多数展示查询。
- 设备行按 ID 复用，不每次重建整个列表。
- 日志面板默认收起；诊断导出在独立进程执行。
- 远端大文件散列/复制已移出 Agent，有并发和队列上限。
- 调试帧日志受 traceFrames 开关控制，不能将其当成默认逐帧日志负担。
- 逐请求 ACL 扫描的旧实现并未接入当前请求路径，不将未使用的 private-state 模块误判为热路径。

## 处理顺序与本次变更范围

先修 Windows 进程检查及初始化阻塞，再拆分界面刷新和恢复等待；随后消除重复调度扫描、空闲轮询和日志重复同步写入；再做文件传输 worker 复用、MCP 目标发现和历史索引。

本次是性能审查，没有宣称上述性能项已全部修复。唯一随审查部署的代码修正是我上一轮日志补丁误植进 PowerShell 字符串的三处 catch，Windows 解析器对任务脚本、会话脚本及进程缺席查询三条路径均通过。未重启当前 5.4/5.6 进程；新启动的执行路径会读取修正文件，现有进程已缓存的模块需在其正常重启后加载。完整修正源码已保存至 `fix/5.6-bounded-diagnostics` 分支。
