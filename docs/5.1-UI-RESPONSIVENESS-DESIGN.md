# 5.1 界面响应与交互修正设计

日期：2026-10-23。基线：`5.1` / `39029af`。

状态：待实施设计。本次只新增文档；以下目标不代表已经完成修复或通过性能验收。

## 1. 要解决的问题与边界

窗口卡顿应在界面、桌面通信和系统调用边界解决。不能为了让按钮流畅，重写已经能工作的连接、执行和传输核心。

继续保持已确认的产品行为：

- 首次授权安装管理员后台服务，以后正常使用不反复确认 UAC。
- 一台连五台、五台连一台可以同时操作，不抢占控制权；断开只影响指定连接。
- 一个程序、一个包，界面独立控制“连接其他电脑”和“允许其他电脑连接本机”，可以同时开启并记住状态。
- 每台设备有主动断开按钮；五台已连接时，第六台触发“保留现有连接／替换 1–5”，用户明确选择才替换。
- 已有设备记忆和自动重连继续沿用，不另做一套。

本次设计不包含旧后台识别、版本比较、更新功能、新的连接协议或新的远程管理功能。配对密码学、SSH、命令执行、SFTP、转发、持久任务和业务重试策略不在重构范围内。

## 2. 已发现的原因

| 位置 | 当前行为 | 后果 |
| --- | --- | --- |
| `desktop/main.cjs`、`agent-client.cjs` | 每次界面请求都先 `ensureAgent`，健康后台也重复做启动检查 | 展示数据反复进入启动检查路径 |
| `private-state.cjs` | Windows 权限检查用同步 PowerShell，单次超时上限 15 秒 | 在 Electron 主进程执行时，窗口事件处理被阻塞 |
| `renderer.js` | 每 3 秒读取两端状态及两端日志 | 每轮产生多次重复权限检查与数据处理 |
| `main.cjs` | 另有每 1.5 秒的容量弹窗状态轮询 | 与远端状态刷新重复，查询阶段缺少完整的在途保护 |
| `renderer.js` | 每轮清空两张设备表并重建所有按钮 | 鼠标焦点、键盘焦点和行内操作可能被刷新打断 |
| `renderer.js` | 正在刷新时直接返回，操作后的刷新可能被跳过 | 操作结束了，界面还停留在旧状态 |
| `renderer.js` | 状态与日志共享一个大异常处理 | 单侧或日志失败，整个页面被标成“后台恢复中” |
| `autostart.cjs` | 服务查询及安装路径包含同步外部进程 | 查询、首次授权期间也可能拖住窗口 |
| `agent.cjs` | 日志接口读取、解析多个完整日志文件再截取尾部 | 高频调用增加后台 I/O 和解析工作 |

隔离调用链检查得到：一次完整刷新有 4 次桌面请求，每次可触发 3 次 ACL 检查，共 12 次；再加两次容量查询，共 14 次。这个数字描述该组调用，不是所有运行状态下固定的每三秒进程数。

注入每次 100 毫秒的模拟 ACL 延迟后，可以重现主线程心跳停顿。这证明同步调用链会阻塞；模拟耗时不能作为用户 Windows 电脑上的实际耗时。真实延迟、资源占用和改善幅度必须在原生 Windows 上测量。

## 3. 设计决定

### 3.1 优先异步化，不增加 Worker

将权限检查、服务查询和安装中的外部命令改为异步调用；保留现有权限校验规则和脚本。`agentClient.request` 仍返回 Promise，Agent HTTP 协议不变。必要的文件读取使用异步接口，不在主进程解析大文件。

本方案不新增 I/O Worker，不增加线程消息转发和生命周期管理。只有完成异步化后实测仍存在无法异步化的阻塞，才另行评估隔离方案。

并发有明确上限：每个角色最多一个状态查询；全局最多一个 ACL 子进程，按队列公平处理；启动配置修改串行执行。等待 UAC 或服务安装时不占用 ACL 队列，也不暂停窗口响应。相同角色、相同只读查询合并在途请求，不合并修改操作。

### 3.1.1 服务与权限的前提

正常运行以首次授权安装管理员后台服务已经完成为前提，不设计普通权限后台作为备用运行模式。首次安装属于一次性流程，不是正常刷新中的检查分支。

管理员后台以 SYSTEM 运行；桌面窗口可以使用登录用户身份运行，通过已鉴权的本地接口访问服务。这不表示后台缺少管理员权限，也不要求用户每次打开窗口再提权。

私有状态 ACL 检查验证的是目录和文件是否被不受信任账户访问或修改，并非检查管理员后台有没有管理员权限。即便服务以 SYSTEM 运行，这项安全验证仍有不同的职责。

正常启动先连接已安装服务。连接失败时才按需查询服务运行状态，区分停止、启动中和通信异常；不能将通信失败直接解释成“没有安装”，不能自动弹 UAC、自动重装或启动普通权限后台。

### 3.2 初始化与日常查询分开

每个角色初始化时连接现有服务，共用初始化中的 Promise。进入正常状态后，刷新直接调用现有查询接口，不再每次调用 `ensureAgent`。发生通信故障时才按需复用既有服务恢复逻辑，不触发安装。

角色状态采用：`初始化中 → 可用 → 暂不可用 → 恢复中`。只有可恢复的传输错误进入单次恢复流程，按有上限的退避重试；同一角色不能同时启动多次恢复。

权限、身份、角色或配置不匹配应明确报错，不能当作普通离线无限重启。服务模式继续复用服务，不能自动降级为普通账户后台。这里的恢复只复用已有角色启动规则，不做旧版本扫描、版本识别或更新。

### 3.3 一个刷新调度器

用“上轮结束后再安排下轮”的调度器，代替相互独立的定时器。初始建议周期如下，实施后按原生实测调整：

| 场景 | 调度 |
| --- | --- |
| 窗口可见 | 两端状态每 3 秒；角色独立失败、独立恢复 |
| 窗口隐藏 | 停止 DOM、日志和近端纯展示查询；重新显示时立即刷新 |
| 允许入站连接的远端 | 隐藏时仍每 3 秒检查，保证第六台请求能弹窗；关闭该功能后停止隐藏轮询 |
| 日志面板展开且窗口可见 | 每 5 秒读日志；关闭后停止读取 |
| 用户完成修改 | 排入一次优先刷新；若已有查询，确保其后再取一次新状态 |

以下内容改为触发式，不设置独立轮询：

| 内容 | 触发时机 |
| --- | --- |
| 服务运行状态 | 本地服务连接失败、用户明确查看服务状态、首次安装结束后；连接正常时不另查服务管理器 |
| 开机启动配置 | 打开相应设置时读取，保存后确认一次 |
| 权限及身份校验 | 每次实际访问按原安全规则执行，不做独立定时检查，也不省略请求时校验 |
| 设备名称、配对列表、默认设备 | 首次加载、相关操作后读取；其他端带来的变化复用状态刷新，不增加独立轮询 |
| 配对码有效期 | 获取时记录到期时间，本地倒计时；到期或提交时确认，不每秒请求后台 |
| 日志导出、诊断信息 | 用户点击时生成 |

连接操作等待期间可临时每 1 秒查询相关角色，成功、失败或超时后恢复常规周期；仍经过同一调度器，不增加并行计时器。自动重连始终由后台完成，不依赖窗口轮询。

远端状态快照同时供设备列表和容量弹窗使用，取消独立的 1.5 秒查询。弹窗展示前按需再确认一次状态；同一请求最多一个弹窗。保留过期检查和后端对所选设备 ID 的校验。

隐藏窗口不能导致第六台请求失去处理机会。弹窗取消、超时、请求失效均保持已有连接，不自动选择某台替换。

日志默认收起，用户展开后加载现有接口的数据。第一阶段只减少无用读取，不改 Agent 日志存储或增加游标协议。若日志仍成为瓶颈，再单独提出有界尾读方案，不混入本次必改范围。

### 3.4 设备行稳定，只更新变化字段

用设备 ID 维护行节点，新增才创建，移除才删除；状态变化只更新对应文字、状态和按钮。设备没有语义变化时不写 DOM。

刷新应保留滚动位置、键盘焦点和当前操作中的按钮。设备排序保持稳定，不因瞬时状态跳动。连接状态来自 Agent 的确认，不用动画或时间戳制造“正在实时刷新”的假象。

近端和远端各自显示“正在读取／最新状态／上次更新失败”，失败时保留最后快照并标注时间。日志失败只影响日志，不把两端一起标成恢复中。

### 3.5 操作有明确的对象和结束条件

- 点击后立即显示等待状态，只锁定该设备相关的冲突按钮，其他设备仍可操作。
- 一次点击对应一个明确的目标设备 ID 和期望状态，避免连续点击对旧布尔值反复取反。
- 修改成功后必须读取操作之后的新状态；不能因 `busy` 直接跳过刷新，也不能被操作前发出的旧响应覆盖。
- 请求失败显示具体原因；超时且结果不确定时显示“结果待确认”，随后查询实际状态，不自动重发修改命令。
- 断开、撤销配对、设为默认继续使用现有业务含义。本次不顺带修改其运行时语义。
- 启动设置串行提交；等待中锁定冲突控件，避免多个保存请求或多个授权提示并发。

首次安装按钮应立即反馈“等待系统授权／正在安装／已完成或失败”。窗口在整个过程可拖动、滚动和查看其他状态。正常启动直接连接已有服务，不主动请求 UAC，也不额外轮询服务安装状态。

## 4. 安全与失败处理

性能优化不能靠省略权限检查实现。

- 每次实际 Agent 请求仍在使用时验证私有状态权限；不长期缓存“ACL 安全”，不因上次成功跳过后续检查。
- 保留目录和文件类型、符号链接、所有者、允许账户、SYSTEM 所属账户以及身份绑定规则。失败关闭访问。
- 只合并同一个在途只读请求、缓存展示快照。快照不作为授权依据，也不能将陈旧状态标为当前已连接。
- 运行时令牌和私有文件留在桌面主进程的受限访问层；Renderer 不接收凭据。继续使用 sandbox、context isolation、固定 IPC 路由和发送方校验。
- 异步请求包含关联 ID 或代次，迟到响应不能覆盖新状态。桌面通信异常只影响界面读取，重新初始化仍走原身份检查，不能关闭远程业务进程。
- 查询使用覆盖排队、ACL 和 HTTP 的总截止时间；取消仅终止该查询及其子进程，不终止服务、连接或远程任务。
- 查询超时与权限拒绝分开显示。配对、安装等长操作沿用各自合理预算，不能统一套用短查询超时。

普通状态查询总预算初始设为 5 秒，在途合并不得无限延长预算。长安装任务采用独立预算和明确阶段；取消界面等待不等于安装已回滚。

## 5. 修改范围与实施顺序

| 步骤 | 主要文件 | 完成条件 |
| --- | --- | --- |
| 1. 建立基线 | 桌面性能检查脚本 | 原生 Windows 记录主进程停顿、查询耗时、子进程数量和资源占用 |
| 2. 移出阻塞调用 | `main.cjs`、`agent-client.cjs`、`private-state.cjs`、`autostart.cjs` | 主进程无同步外部命令；原权限规则不变；长系统操作不冻结窗口 |
| 3. 合并刷新和恢复 | `main.cjs`、`renderer.js` | 正常轮询不反复 ensure；容量检查复用快照；每个角色单独恢复 |
| 4. 修正渲染和操作反馈 | `renderer.js`、必要的 preload 消息及样式 | 不整表重建；操作后刷新可靠；状态和日志错误独立 |
| 5. 验收与交付 | 检查脚本、开发和打包入口 | 开发模式及 Windows 包均通过；交付单文件夹运行包，无开发缓存 |

共享客户端和权限模块仅增加异步执行路径及必要的截止时间处理，不改连接业务。每步单独可验证、可回退，不一次性重写全部桌面层。不引入前端框架、数据库、常驻日志服务或自动更新组件。

## 6. 验收标准

以下是实施目标，需在同一台 Windows 机器、相同连接和日志负载下记录修改前后数据。不能用 Linux 或模拟延迟结果替代原生 Windows 验收。

### 窗口响应与后台开销

- 空闲和五连接刷新期间，点击本地按钮到显示等待反馈的 P95 不超过 100 毫秒。
- 稳态主进程事件循环延迟 P95 不超过 50 毫秒；无周期性同步 PowerShell 导致的百毫秒级冻结。单独记录系统对话框及系统负载干扰。
- 给权限查询注入 1 秒、5 秒和超时延迟，窗口仍可拖动、滚动和操作无关设备，不产生重复请求堆积。
- 正常状态、日志关闭时，每轮仅两端各一个状态请求及各自必要的 ACL 检查；没有额外健康查询和独立容量轮询。主进程同步外部命令次数为零。
- 设备内容不变时不删除、重建设备行；刷新期间焦点和滚动位置不丢失。
- 记录应用进程树 CPU、内存、子进程峰值和磁盘读取；隐藏后查询及日志工作量下降，持续运行 30 分钟无无界队列或内存增长。性能报告同时列出机器规格和系统总压力。

### 交互与既有功能

- 启动、单侧离线、慢查询、日志失败、安装等待分别呈现真实状态；一个模块失败不覆盖其他模块正常状态。
- 连续点击、操作与刷新交错、迟到响应、断开后重连，均不覆盖新状态、不重复提交修改。
- 一台连五台、五台连一台同时执行；逐台断开只影响所选连接。
- 第六台弹窗分别验证保留和替换 1–5；窗口隐藏、请求超时、被选连接已离线时也不误替换。
- 首次安装授权一次；正常重开不重复 UAC；两种功能开关和原有记忆状态保持。
- 权限被放宽、文件被替换为符号链接、身份或所有者变化时仍拒绝访问；窗口保持响应，不能为性能绕过校验。

开发模式和最终 Windows 包都要实际启动。截图用于核对布局、按钮状态和错误提示；交互及连接正确性必须靠实际操作和记录验证，不能用截图代替。
